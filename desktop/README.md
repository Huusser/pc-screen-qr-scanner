# PC 屏幕框选扫码（桌面版 M0）

在 PC 上框住屏幕上任意二维码，实时读出内容。用于「手机不在手边、但流程要求扫码」的场景（例如在 PC 微信里打开小程序被要求扫码绑定账号）。

## 怎么用

双击 `start.bat`（首次会自动装依赖），弹出小窗口后：

1. 点「▶ 开始框选」，或按 `Alt+Shift+Q`（窗口可以拖边角改大小、点标题栏 □ 最大化，见下节）
2. 屏幕会被冻结并变暗，中央有一个取景框（底部有「拖动鼠标框住二维码」的引导卡）
3. 把框拖到二维码上（拖框内移动、拖角/边拉伸、双击复位）
4. 识别成功后底部换成结果条：徽标是结论，下面是步骤，右下角是主按钮
5. `C` 复制 · `空格` 或点顶栏 `冻结` 胶囊切连续 · `R` 重置框 · `Esc` 退出框选
6. 结果条右侧 `✕` 可收起回到框选；顶栏 `?` 看快捷键；`✕` 退出框选

识别出**业务链接**类二维码时的推荐做法：
复制 → 打开 PC 微信「文件传输助手」→ 粘贴发送 → 在聊天里点开这条链接（微信内置浏览器自带你的微信登录态）。

## 界面

- **主窗口**（`launcher.html` + `launcher.js`）：无系统边框，自绘标题栏；大按钮开始框选，两张卡片显示「微信环境」「移动端环境」；
  代理运行时切换成橙色倒计时横幅 + 「接下来」三步，标题区和扫描流程自动让位。
- **取景框**（`overlay.html`）：左上角一块深色工具条放全部状态胶囊（浅色页面上也看得清），右上角 `?` / `✕`；
  未识别时底部是引导卡，识别后换成结果条；连续模式下框内有一条扫过的光线。
- **询问卡**：两个选项做成可选卡片，选中项带对勾与高亮；主按钮文案随选项变化（`启用并在微信打开` / `复制并打开微信`）。
- **设置面板**：点标题栏齿轮进入，四页（扫码 / 移动端 / 外观 / 关于），标题栏变「← 设置」。

## 窗口尺寸与最大化

主窗口可以自由拖四条边、四个角改大小，标题栏右侧依次是「设置 · 最小化 · 最大化 · 关闭」。

| 约束 | 值 | 为什么 |
| --- | --- | --- |
| 最小尺寸 | **400 × 460** | 再窄状态卡会被挤成一条缝，设置页的分段控件开始折行 |
| 最大尺寸 | **当前显示器工作区** | 超过屏幕会出现标题栏够不到的情况；上限随窗口移动到的屏幕自动切换 |
| 内容最大宽度 | **680px** | 窗口拉宽时内容居中、两侧留白，不跟着横向拉伸 |

- 最大化后按钮图标变成「还原」（两个叠框），再点一次或双击标题栏即可还原；状态由主进程 `maximize`/`unmaximize` 事件回传，图标不会和真实状态脱节。
- 布局全部用 flex + `minmax(0,1fr)` + `max-width` 自适应，改尺寸时不重排 DOM，所以不会出现错位、重叠或闪烁。
- 窗口拉高时内容块垂直居中（`justify-content: safe center`），拉矮时退化成顶部对齐并可滚动，顶部内容不会被裁掉；底栏固定在最底部，最小尺寸下「退出程序」始终可见。

## 提示音

「识别成功时提示音」是个总开关，音色单独一行选。改音色的交互是**点右侧按钮 → 向下展开 → 选中即收起**，收起的同时会把选中的音放一遍，所以不需要再点一次试听。

### 内置音色

六个音色全部由 `sound.js` 用 WebAudio 现场合成，不打包音频文件（安装包不增大，也没有音频授权问题）。6 个音做**等响度归一**（`trim` 系数），切换时不会一个震耳一个听不见。

| # | 音色 | 时长 | 声音构成 | 适合 |
| --- | --- | --- | --- | --- |
| 01 | 经典扫码嘀 | 180ms | 1760Hz + 高次泛音 | 连续扫多张，只要"扫到了" |
| 02 | 双音上行 | 280ms | C6→G6 纯五度 | 默认；扫一次等一次结果的节奏 |
| 03 | 马林巴轻敲 | 350ms | E6 基音 + 2/3 次泛音 | 安静环境、长时间使用 |
| 04 | 木质轻叩 | 150ms | 噪声瞬态 + 双共振峰 | 开会、共享屏幕、怕吵 |
| 05 | 清亮双叮 | 320ms | G6+C7 + 非整数泛音 | 外放音量小、嘈杂环境 |
| 06 | 三连上行琶音 | 440ms | C6-E6-G6 琶音 | 一天只扫几次，要明确"结束了" |

### 自定义音色（导入）

设置页「提示音音色 → 自定义」会弹系统文件框。导入分两跳，**先认格式、再真解码**：

1. 主进程按**文件头**（magic bytes）判断真实格式，不看扩展名 —— 网上下的音效经常 `.mp3` 实为 mp4、`.wav` 实为 flac。
2. 渲染进程用 `AudioContext.decodeAudioData` 真解一次，解不开就是不能用（格式表只能说明"大概支持"）。
3. 解开的音频重编码成 **16bit WAV / 44.1kHz / 最多双声道 / 峰值归一到 0.9**，存 `desktop/sounds/custom.wav`，元信息写进 `settings.json` 的 `soundCustom`。

**为什么存 WAV 而不是原文件**：用户随时可能删掉或移动源文件，而提示音要跟着走。存归一后的 WAV 就不依赖外部路径，格式也确定，不会出现"下次打开播不出来"。

#### 识别范围

| 能导入（内置解码器可解） | 格式 |
| --- | --- |
| 有损/无损音频 | **MP3**、**WAV**、**FLAC**、**M4A/MP4(AAC)**、**AAC(ADTS)**、**OGG(Vorbis)**、**Opus**、**AIFF**、**WebM/MKV(音频轨)** |

| 认得出但不支持（会给结论，不浪费一次解码） | 原因 |
| --- | --- |
| WMA / ASF / WMV | Windows Media 私有编码，Chromium 无内置解码器 |
| APE / WavPack / TTA / Musepack | 无损或专门压缩，Chromium 无内置解码器 |
| ALAC(M4A) | 苹果无损编码 |
| Speex(OGG) | 早期语音编码 |
| AMR / AMR-WB | 功能机语音编码 |
| MIDI | 存的是乐谱不是声音，需要音源 |
| AC-3 / E-AC-3 | 影院多声道 |
| CAF / AU / RealAudio / DSD | 容器或编码不在支持范围内 |

#### 失败处理

所有失败都带**具体原因 + 补救办法**，不会只弹"导入失败"：

| 情况 | 提示 / 处理 |
| --- | --- |
| 用户取消文件框 | 静默返回，不提示、不打扰 |
| 认不出的二进制 | 「认不出这个文件的音频格式」+ 支持的格式清单 |
| 网页被存成文件（`<!DOCTYPE`/`<html` 开头） | 「这是一个网页而不是音频文件」 |
| 认得出但不支持（上表） | 「识别为 WMA，但……请先转成 MP3 / WAV / M4A / OGG」+ ffmpeg 用法 |
| 文件 > 24MB | 拒绝，并说明提示音通常只有几十 KB |
| 0 字节 / 读不到 / 非文件 | 各自的具体原因 |
| 解码失败（损坏、加密、非音频流） | 「内编码解不开」+ 已识别出的格式名 |
| 时长 < 0.04s 或 > 20s | 拒绝，20 秒以上不适合当提示音 |
| 整段接近静音 | 「导入后也听不到」 |
| 写盘失败 / 不是合法 WAV | 拒绝并且**保留原来的 custom.wav**（先写 `.tmp` 再改名） |

扩展名与实际格式不一致**不拦**，只是导入成功的提示里说明一句「已按实际内容导入」。

## 全自动打开链接（搜一搜 → 代点第一条）

扫码后把链接交给微信，这一步原来要靠人：粘贴到文件传输助手 → 发送 → 点链接。

现在改成走微信「搜一搜」：工具把链接填进搜索框并回车，停在结果页。开关决定最后那一下：

| 开关 | 行为 | 会不会点鼠标 |
| --- | --- | --- |
| **关**（默认） | 自动填好搜索词并回车，停在结果页，你自己点第一条 | **不会** |
| **开** | 连"点第一条结果"也代做，点完校验是否真的开了网页 | 会，按下面选的方式定位后再点 |

### 三种定位方式（设置里四选一）

微信 4.x 起聊天区是 Qt 自绘（`MMUIRenderSubWindow*`），UIAutomation 拿不到聊天控件；
结果第一条用 `↓`、`Tab` 也选不中（实测）。所以最后一下只能"看着屏幕点"——
而"看"有三种办法，各有各的适用范围：

| 值 | 界面显示 | 怎么做 | 什么时候好用 |
| --- | --- | --- | --- |
| `auto` | 自动（默认） | 依次尝试 无障碍 → 文字识别 → 区域，任一种命中就点 | 不想管细节 |
| `uia` | 无障碍 | 走 UI Automation 树，找名字含「访问网页」的元素，取它的可点坐标 | 微信网页层暴露了无障碍树时最干净 |
| `ocr` | 文字识别 | 截图 → Windows 内置 OCR 找「访问网页」四个字 → 点文字中心 | 微信只改了排版、字还在时最抗改版 |
| `region` | 区域 | 扫截图找"第一条结果那张浅色大卡片"→ 点卡片中央 | 前两种都取不到时的兜底 |

位置：设置 → 扫码 → 「交给微信」分组。总开关关着时，「点击方式」整行会压暗且点不动——
顺序上它是开关的下级选项，不是独立功能。

**老版本的"标定"已删除。** 它依赖一次性记住的绝对位置 + 图样指纹：换窗口大小、
换分辨率、微信改版都会失效，使用场景一多就不适用。

### 怎么认出「我们的微信」：按进程树，不按进程名

WeChat 4.x 既不是一个窗口，也不是一个进程。本机实测（4.1.13.12）：

```
Weixin.exe（拥有主窗口）
  ├─ Weixin.exe ×4                  渲染 / 辅助
  └─ WeChatAppEx.exe ×12            内置浏览器 + 小程序宿主  ← 搜一搜结果页在这里渲染
WeixinUpdate.exe ×1                 另一棵树，但它的窗口标题也叫「微信」
```

两种天真做法都会错：**按进程名**只认 `Weixin.exe`，会漏掉 `WeChatAppEx`——而结果页
恰恰是它渲染的；**按窗口标题**又会撞上更新插件那个标题同样是「微信」的窗口。

所以现在**认进程树**：从拥有主窗口的 `Weixin.exe` 出发，把它全部子进程收进「微信家族」。
这一步同时解决两件事——`WeChatAppEx` 自动纳入，`WeixinUpdate` 自动排除（它的父进程
不在这棵子树里）。

| 判定 | 以前 | 现在 |
| --- | --- | --- |
| 前台是不是微信 | 句柄必须**等于**主窗口 | 前台窗口的 pid **属于家族** |
| 该截 / 该点哪个窗口 | 固定主窗口 | 家族里**前台那个** → 否则主窗口 → 否则最大的 |
| 点击落点是否安全 | 前台窗口是不是主窗口 | `WindowFromPoint` 查**这一像素属于谁** |

最后一行是关键：点击是否安全取决于「这一点会点到谁」，而不是「焦点在哪」。
所以微信被别的窗口挡住时会拒绝，而不是点穿过去。

服务端每次交接只跑**一次** `wxprobe`，由它定下"哪个 pid 集合算微信"，全程沿用。
「该动哪个窗口」这个问题晚一点才问，**在 `keys` 里问**：敲完键、结果出来之后，
结果页可能已经搬进 `WeChatAppEx` 自己的窗口——那时截图和坐标都要以那个窗口为准，
否则整体会偏移一个主窗口的距离。所以 `keys` 在等完结果之后调一次 `Select-WxTarget`，
把 `target` / `targetHow` / `targetRect` 一并带回来。

这曾经是第二次 `wxprobe`（另起一个进程，1.4~1.7 秒，重新枚举一棵没变过的进程树，
六次真实运行的答案都是 `main`）。选窗口本来就是 `Select-WxTarget` 一个函数的事，
实测在 `keys` 里只多 **87ms**（一次 `EnumWindows` + 一次 `GetWindowRect`）。
代价是"微信在这几秒里重启过"检测不到，但那是 fail-safe：
`click` 用 `WindowFromPoint` 校验落点 pid，认不出来就直接拒绝。

### 三条硬约束

- **找不到目标就不点**，不按比例猜，也不试"大概是这儿"。
- **敲键前校验前台属于微信家族**（含内置浏览器宿主），不属于就放弃——绝不把 URL 打进别的窗口。
- **点完必须校验**：在 4 秒窗口内每 250ms 探一次，三种证据任一成立就算打开——
  ① 冒出了新的、有标题的顶层窗口；② 被点窗口的标题变了；③ 被点窗口的客户区画面变了。
  这条以前只认 ①，于是**网页开在微信当前窗口里时永远判"没打开"**，用户明明看到了网页却收到失败通知。
  现在 ③ 兜住了这种情况（一次 `StretchBlt` 把**点击点周围 400×400** 压成 32×32 灰度，和点击前的基线比平均差；
  以前压的是整个客户区 24×16，跳转信号被稀释到 7~10，离阈值 6 只剩 1 个单位的余量，所以偶发"点了没反应"的误报）。
  只有四种证据全部落空才判失败，且**不重试、不乱点**。
  "新的窗口"是拿**点击前一瞬**的快照比的（`click` 自己拍的），所以"结果页自己开了个窗口"不会被误算成点击的功劳。

`auto` 的降级只发生在"定位"阶段：某一种找不到就换下一种；一旦真的点了手，
就不再换点重试。

### 各方式的已知边界

- **无障碍**：树里的名字必须含「访问网页」。微信若关掉网页层无障碍，或把措辞换掉，这一种就取不到。
- **文字识别**：需要系统的中文 OCR 语言包（`zh-Hans-CN`）。缺了会报 `no-chinese-ocr`，
  不影响另两种；深色主题 + 字号很小时识别率会下降。
- **区域**：认的是"比背景明显亮、高度 62~420px 的横向条带"，搜索框（约 40~48px）会被排除；
  微信若把第一条换成纯文字列表（不再是大卡片），这一种会失手。

### 前提

- 微信 4.x（本机 4.1.13.12 实测），且左侧栏有「搜一搜」
- 微信「设置 → 通用设置 → **使用系统默认浏览器打开网页**」**不能勾**——勾了会把链接踢到 Chrome，微信会话丢失，授权拿不到 code

### 实现分布

| 文件 | 职责 |
| --- | --- |
| `win-helper.ps1` | `wxprobe`（认进程树 + 选目标窗口；`-Full` 才解析进程名，那是诊断信息）、`keys`（恢复/抢前台轮询/家族校验/SendKeys/就绪轮询/**选目标窗口**/截图）、`click`（落点校验 + 点击 + 轮询判定 window/title/pixels）、`hit`（查某点属于谁，只读）、`uiafind`（按 pid 集合走 UIA 树；无果时每 120ms 复查、最多 8 遍——无障碍树比画面慢约 700ms，短间隔轮询比长睡划算）、`ocr`（WinRT OCR）、`shot`（可指定窗口）。**两种跑法共用同一套动作体**：`-Action xxx`（一次性子进程）与 `-Serve`（常驻，收发一行 JSON）。Win32 P/Invoke，纯 ASCII，DIP 感知，输出单行 JSON |
| `wechat-auto.js` | 编排时序；常驻 worker 的生命周期（启动/超时/重启/关闭）；`probeTarget` 认亲（`{full:true}` 才要进程名）；三种定位 `findUia` / `findOcr` / `findRegion`；窗口比对；`auto` 降级 |
| `main.js` | IPC `qr:wx-open`，先关取景框（它置顶且开了内容保护，不关截图是黑的）；`whenReady` 预热 worker、`will-quit` 关掉它；`--wxtest` |
| `test-wx-result.html` | 仿「搜一搜结果页」，上一轮验收 region / ocr 用的靶子；当前 `--wxtest` 不再调用 |

### 常驻 worker（默认路径）

以前每个动作都起一个全新的 `powershell -File win-helper.ps1 -Action ...`，
每次都重付「进程启动 + 解析脚本 + Add-Type 编译 C#」（约 450ms）和「卸载程序集 + 退岀」（约 450ms）。
一次交接 4 个动作，就是 **3.4 秒、占整条链路 40%**，而这笔钱跟"做什么动作"毫无关系。

现在启动时拉一个 `-Serve` 常驻进程，一行 JSON 进、一行出：

```
{"id":3,"a":"keys","o":{"wait":1500,"pids":"1,2,3","win":133400}}
{"id":3,"ok":true,"rect":{...},"target":{...},...}
```

- **协议**：`a` = 动作名，`o` = 参数（短名：`wait`/`pids`/`win`/`x`/`y`/`keys`/`target`/`file`/`hwnd`/`poll`/`full`）。
  缺字段一律按默认值补齐（`Get-Opt`），**每个请求开始前都重置一遍** —— 否则上一轮的点坐标会漏到下一轮。
- **启动时机**：`app.whenReady()` 立刻拉起来。进程启动 + 编译 + 预热约 1.2~1.9s，正好落在用户还在扫码的那几秒，
  对用户免费（`boot.log` 会记 `worker warm NNNms`）。
- **超时**：沿用每个动作原有的超时（`keys` 25s / `click` 18s / 其余 15s）。超时即判死 -> 关 stdin -> 强杀 ->
  下一次调用自动拉起新的；**连续重启上限 2 次**，超过就报 `worker-restart-limit` 而不是无限重试。
- **退出**：`will-quit` 关 stdin（这是 worker 唯一的退出信号），进程内还有一个 `process.on("exit")` 兜底。
- **回退开关**：`set QRSCAN_WORKER=0 && npm start` 走原来的一次性子进程路径。
  它既是出问题时的退路，也是在同一台机器上直接 A/B 对比两条路真实差距的唯一办法。
- **验收**：`boot.log` 的 `wx-open ... worker=worker/restarts=0` —— `restarts` 应为 0。
- **调试单个动作**：直接跑一次性模式，比对着 worker 猜要快：
  `powershell -NoProfile -File win-helper.ps1 -Action hit -X 100 -Y 200`

### 自测（`--wxtest`）

只覆盖「按进程树认亲」和「点击后怎么判定成功」这两处改动，全程不对真实微信点击或按键：

| 用例 | 怎么测 | 判据 |
| --- | --- | --- |
| `tree` | `wxprobe` 读真实微信的进程树（只读） | 家族里有 `Weixin`、有 `WeChatAppEx`、**没有** `WeixinUpdate`，且 `pidsFrom = tree` |
| `uia` | 靶子 = WinForms 窗口（按钮文字是「访问网页」） | 传「无关 pid + 靶子 pid」能命中；只传无关 pid 必须不命中 |
| `click` | 在靶子上同一像素点两次 | 传靶子 pid → 点；传无关 pid → 拒绝且 `why = point-outside-family`，鼠标不动 |
| `feedback` | 靶子客户区切成几块，分别只改画面 / 只改标题 / 什么都不改 | 依次判成 `pixels` / `title` / `none`；`pixels` 是修误报的关键——网页开在微信当前窗口里时没有新窗口，只有它能成立 |
| `keys` | `-Keys ""`，只跑"抢前台 → 校验"，一个键都不发 | **参考项，不计入通过**：靶子是后台起的进程，Windows 前台锁经常不给它前台。传无关 pid 必须 `not-foreground` |
| `logic` | 纯函数 | `planModes` 顺序；`diffWindows` 只算新增；`freshWindows` 再剔微信内部窗口 |
| `live` | 真实微信上只读跑一遍 | **不判失败**，只记录 `familyWindows` 供观察（微信没停在结果页时本来就找不到） |

产物在 `desktop/wx-test/`：`report.json` + `live.png`。
`ok: true` 表示 `tree` / `uia` / `click` / `feedback` / `logic` 全过；`keys` 是参考项，`live` 只是现场快照。

想确认「结果页到底在不在 `WeChatAppEx` 的窗口里」：在微信里搜一次、把结果页停在屏幕上，
再跑一次 `--wxtest`，看 `report.json → steps.live.family.windows` ——
如果出现一条 pid 属于 `WeChatAppEx` 的窗口，就说明结果页确实搬到了独立窗口，
运行时会自动选中它（`targetHow: foreground`）。

### 分段计时（临时设施，用完可整体删）

给「扫码 → 微信里点开第一条」这条链路做逐段计时，用来定位延迟。**纯附加代码，删掉不影响任何功能。**

每次真的走一次「全自动打开链接」（扫码或手动交接），就会往 `desktop/timing.log` **追加**一段记录：

```
 ═══════════════════════════════════════════════════════════════════════════
  wx-open · 2026/10/23 18:30:12 · click=true mode=auto
 ═══════════════════════════════════════════════════════════════════════════
  #  区间(ms)       耗时    占比   节点                负责什么
  ─────────────────────────────────────────────────────────────────────────
  1  12 → 352        340    6.3%  overlay-close       关闭全屏取景框，再等 340ms 让它真正消失
  2  352 → 2872      2520   46.8%  probe-pre          第一次认亲：进程树的 pid 集合与主窗口
  ...
 ─────────────────────────────────────────────────────────────────────────
     合计             5386 ms

  ── 底层调用明细 ──
  次  动作      模式    总耗时  boot   work   tail   固定占比  说明
  1   keys      worker     2841     2   2705    134        5%  抢前台 + Ctrl+F/粘贴/回车 + …
  2   wxprobe   worker      516     2    498     16        3%  认亲：进程树 + 目标窗口
  ─────────────────────────────────────────────────────────────────────────
      合计                 3357     4   3203    150        5%  共 2 次调用
```

**两个表分别回答两个问题：**

- **阶段表**：哪一段在花时间。节点从左到右就是代码的执行顺序，`负责什么` 一列说明这一段干了什么。
- **调用明细**：慢在「起进程」还是慢在「干活」。每次调用都被拆成三段，`固定占比` 一列就是这台机器的"冤枉钱"：
  - `worker` 模式（默认）：`boot` ≈ 请求分发（0~3ms），`work` = 动作本身，`tail` = 管道往返 + JSON 解析。
    固定开销应当只剩几十毫秒 —— 如果这一列又变回几百毫秒，说明那一次悄悄退回了 `spawn`。
  - `spawn` 模式（`QRSCAN_WORKER=0`）：`boot` = 启动 + 解析 + 编译 C#（约 850ms），
    `tail` = 序列化 + 卸载 + 进程退出（约 750ms）。**与做什么动作无关，每次都要重付。**

`work` 一列在两种模式下同口径，可以直接跨批次比较。

`timing.sample.log` 是格式样例（用 `hit`/`windows`/`wxprobe` 三个只读动作生成的），可以直接删。

**「等结果」那个 1500ms 可以不改代码就试**：`WAIT_RESULT_MS` 支持环境变量覆盖，

```bat
set QRSCAN_WAIT_MS=600 && npm start
```

允许 0~6000，非法值或未设置一律回到 1500。实际生效值会写进表头（`wait=600`），
所以 600 和 1500 的批次混在同一份 `timing.log` 里也分得清。这是为了测「到底需要等多久」——
跑 600/900/1200 各三次，看 `uiafind` 是否仍稳定命中同一个坐标。

| 想关掉 | 做法 |
| --- | --- |
| 临时静默 | 把 `timing.js` 顶部的 `ENABLED` 改成 `false`，所有埋点立刻变空操作 |
| 彻底删除 | 删 `timing.js` + `timing*.log`；搜 `T.mark(`、`T.meter(`、`T.begin`、`-- 分段计时`；再删 `win-helper.ps1` 里的 `$SW` / `$BOOT` / `emitAt` 注入 / warm-up 那几处 |

## 扫码登录 / 绑定：能不能不用手机

顶部会显示微信状态。出现 **`微信 4.x 已登录 · 快速登录可用`** 说明本机具备免扫码能力。

| 码内容 | 工具给的结论 | 你要做的 |
| --- | --- | --- |
| `open.weixin.qq.com/connect/qrconnect` | ✅ 能，走快捷登录 | 点蓝色按钮「用微信快捷登录」→ 浏览器打开 → **页面自动显示你的头像**，点头像确认，全程不扫码 |
| `<租户>.zhiye.com/.../ScanQR?key=...`（北森招聘系统等自建扫码登录） | ⚠️ 能，但要换手机环境 | 点蓝色按钮「手机环境打开」→ 确认「模拟手机微信」→ 取景框自动收起、微信被唤起 → 文件传输助手粘贴发送 → 点开 → 授权后自动回结果页 |
| `open.weixin.qq.com/connect/oauth2/authorize` | ⚠️ 只能在微信内 | 复制 → 文件传输助手 → 在聊天里点开 |
| `weixin://...` | ✅ 能 | 点「唤起微信打开」 |
| 自有域名 + token | ✅ 能 | 复制 → 文件传输助手 → 点开；或直接粘贴进绑定框 |
| 纯 token | ✅ 最容易 | 直接粘贴到绑定输入框 |

**关于「手机环境打开」**：它不是常开功能。平时代理进程根本不存在、系统代理一个字节都不动；
只有你点这个按钮并在弹卡里确认「模拟手机微信」之后，才会临时起一个本地代理把微信内置浏览器的 UA
换成 Android 微信，然后必然在倒计时结束（默认 3 分钟）时自动关闭并还原。
完整机制见项目根目录的 `扫码登录-移动端代理触发机制.md`。

顺序上有一处刻意的安排：**先起代理 → 再装根证书（含回查）→ 最后才改系统代理**。
所以证书装不上时（组策略禁止、安全软件拦截、脚本被隔离），系统代理根本没被改过，
界面也不会显示"已启动"，而是把那句原因（来自 `proxy\last_exit.json`）直接弹出来。

端口也不用管：默认代理口 8888、管理口 8899，**被占用会自动顺延**（各顺延最多 20 个，
管理口会避开代理口）。装了 Fiddler/Charles 的机器以前会在这里整体失败、只报"启动超时"，
现在照常可用；真被占满时提示会直接说"端口 8888 已被其他程序占用"。

范围也自动处理：默认**只接管这条链接所在的站**（连同它的父域一起，例如
`<tenant>.zhiye.com` → 连 `zhiye.com`），登录流程 302 跳到别的域时，代理会在把跳转
写回浏览器**之前**把新域名加进范围并换 PAC 版本号——所以既不会把整机流量都解密，
也不会因为跨站跳转而白屏。想全量（或全局代理）在设置里切换；"全局"模式因为
`ProxyOverride` 做不了按域收窄，只能全量，此时范围选项会置灰。

这套规则是按链接形态通用设计的，不挑站点：

- **父域宽化**最多 3 级，PAC 用后缀匹配，深子域（`q.r.s.example.com`）也被覆盖；
- **两段式国家后缀**（`com.cn` / `com.tr` / `co.jp` …）不会当成公司域收进范围——
  判定用"类别词规则"（倒数第二段是 com/net/org/gov/edu/ac/co 即视为注册局后缀），
  新国家后缀出现不用改代码；
- **二维码内容不是纯 URL**（如"登录链接：https://… 请用微信打开"）也能提取出链接；
- 真正算不出域名的（非 http(s)、纯 IP 之外的特殊链）退回全量并写日志。

**关键原理**：微信 3.9.11 for Windows 及以上版本有「快速登录」——当网站用微信登录时，只要本机微信已登录，会优先让你**点头像确认**，而不是扫码。本工具做的事情是：把屏幕上那个码里的登录链接取出来，用浏览器打开，让这个机制生效。之前没有工具时，你只看到一张二维码，不知道它背后是一条可以直接打开的链接。

**两个必须知道的坑**：

1. Chrome 142 及以上版本会弹「允许访问本地网络」提示，**不点允许，快捷登录按钮就不会出现**。看到就点允许。
2. 如果打开后页面仍然只显示二维码、并写着「请使用微信扫描」，说明该站点强制校验「手机扫码」这个动作本身，PC 端无法替代。这类只能换路径（见下表）。

## 码型判别（这是本工具的核心价值，不只是"读出来"）

| 码内容 | 结论 |
| --- | --- |
| `open.weixin.qq.com/connect/qrconnect` | ✅ 快捷登录，不用手机 |
| `*.zhiye.com/.../ScanQR?key=`（北森等自建扫码登录） | ⚠️ 授权能过，但结果页 `/wxAuthResult/*` 只在移动端包里注册，PC UA 打开就是 404 → 需「手机环境打开」（2026-10-22 实测） |
| `mp.weixin.qq.com` 等确认页 | ⚠️ 浏览器试一次，被拦则放弃 |
| `weixin://` | ✅ 直接唤起微信 |
| 自有域名业务链接 | ✅ 复制→文件传输助手→点开 |
| 纯 token | ✅ 直接粘贴到绑定输入框 |

**北森扫码登录实测结论（2026-10-22，<tenant>.zhiye.com）**：二维码内容是
`https://<租户>.zhiye.com/api/Login/ScanQR?key=<32位>&userId=0`。该链接普通浏览器打开被拒
（「查看方式有误 / 请前往微信进行查看」），但在微信 UA 下会 302 到
`appconnect.recruit.91paas.cn/.../NewPortalWechat/authorize` →
`open.weixin.qq.com/connect/oauth2/authorize?scope=snsapi_userinfo`（公众号网页授权）。
也就是说身份由"打开链接的浏览器"提供——PC 微信内置浏览器同样具备，所以**不需要手机**。

## 数据目录、系统要求与打包

### 可写状态在 `%APPDATA%\ScreenQR\`

程序目录（含 `Program Files`）**只读**。设置、日志、代理证书全部落在数据目录：

```
%APPDATA%\ScreenQR\
  settings.json        设置（删掉即恢复默认）
  boot.log crash.log   启动标记 / 崩溃
  timing.log           分段计时（临时设施）
  proxy\
    certs\             本机现场签发的根证书与叶子证书
    previous.json      启用代理前的系统代理备份（用于还原）
    last_exit.json     最近一次启动失败的原因（给界面显示，90 秒内有效）
    manager.log mitm.log proxy-debug.log
```

老版本把状态写在程序目录；首次启动会**复制**到数据目录（不删原件），升级不会丢设置。
路径解析集中在 `desktop/paths.js`：`dataDir()` 数据目录、`proxyDir()` 代码目录（打包后在
`resources\proxy`）、`proxyDataDir()` 代理数据目录。可用环境变量 `QRSCAN_DATA_DIR` 临时改数据目录（便于测试）。

### 系统要求（公开发布口径）

- **Windows 10 1809 及以上 / Windows 11，x64**。Win7/8/8.1 不支持（Electron 31 的 Chromium 已放弃）。
- 依赖系统自带能力：PowerShell 5.1、.NET Framework 4.x、WinRT OCR（**需中文 OCR 语言包**；Win N 版缺媒体功能包则不可用）。
- 「手机环境」**不再需要用户另装任何东西**（自 0.4.0 起）：
  - **Python**：发行包内置官方 embeddable 运行时（`vendor/python`，CPython 3.12，约 21 MB），
    启动代理时优先用它；只有这份文件被删/被隔离时才回落到系统 Python；
  - **openssl**：不再需要。证书签发改成纯 Python 实现（`proxy/certgen.py`）。
  - 设置 → 移动端 顶部的「手机环境依赖」仍会显示实际用的是内置还是系统 Python，便于排查。
- 微信需为 **4.x 中文版**；英文/繁体界面下文字识别与无障碍定位会找不到「访问网页」。
- 多显示器：目前只覆盖鼠标所在那一屏。

### 内置 Python 运行时

```bash
npm run runtime           # 下载 python-3.12.10-embed-amd64.zip 并解到 vendor/python
npm run runtime -- --force # 重新下载
```

- 来自 python.org 官方 embeddable 包，**SHA-256 已钉死**在 `tools/fetch-runtime.js` 里，换版本要同步改。
- 解压即用：不写注册表、不进 PATH、不需要安装程序。
- 打包时通过 `asarUnpack: ["vendor/python/**"]` 解到
  `resources\app.asar.unpacked\vendor\python`（asar 里的 exe 无法被外部进程执行，
  必须解出来；`win-helper.ps1` 同理）。
- 为什么不 PyInstaller：代理脚本只用标准库，`embeddable` 就是官方裁剪版解释器，
  没有自解压 PE 特征，也不会每次改代码都要重新打包。

### 打包与签名

```bash
npm install                     # 需要网络（electron + electron-builder）
npm run runtime                 # 下载内置 Python 运行时到 vendor/python（发布前必跑）
npm run prepare:builder         # 预热打包缓存（换机器/清缓存后必跑；详见下文）
npm run icon                    # 重新生成 build/icon.ico（已有产物，通常不用跑）
npm run dist                    # 未签名安装包 → dist/ScreenQR-<版本>-x64.exe
npm run release:dev             # 自签管线（验证签名链路是否通，产物不可对外）
npm run release                 # 正式管线：需证书（见下）
npm run verify:sign             # 复核产物签名状态（谁签的、是否受信任、有没有时间戳）
```

- 配置在 `package.json → build`：`extraResources` 把 `../proxy` 装到 `resources\proxy`
  （代码进包；`certs`、日志、`_t_*.py` 测试脚本、**所有 `*.html`**、`README.md` 都不进包——
  `*.html` 是分析 404 时抓下来的第三方页面正文，会含业务数据，故用 `"!**/*.html"` 覆盖子目录）；
  `files` 排除了日志（含子目录）、`settings.json`、测试产物、`ui-preview/**` 与 `probe-login.js`。
  `testqr.html` 是**有意保留**的：`--uitest` 要用它对打包产物做界面回归。
  `proxy/README.md` **不再进包**（2026-10-25 二次取舍）：纯文档、零代码依赖，
  安装目录里没人会翻，删它零风险；仓库里仍保留给审阅者。
- 发布前对产物自查一遍：`resources\proxy` 下不应出现 `*.html` / `*.log` / `README.md` / `certs\` / `_t_*.py`。
  三个命令行出口：`--selftest`、`--envcheck`、`--appinfo`。
  另有五个不启 Electron 的回归脚本在 `tools/`：`_t-proxy-error.js`（失败原因能否显示）、
  `_t-proxy-ports.js`（端口顺延）、`_t-proxy-notify.js`（通知时长文案）、
  `_t-proxy-scope.js`（--scope 参数）、`_t_ca_guard.py` / `_t_port_guard.py` / `_t_scope.py`
  在 `proxy/`（证书停手、端口占用、302 同步学习）。
- **签名不用 electron-builder 自带链路**。它要下载 `winCodeSign`，而那个包里带 macOS
  符号链接，没有"创建符号链接"权限的 Windows 上 7za 解压会直接失败（本项目实测卡在这一步）。
  改用系统自带的 `Set-AuthenticodeSignature`：`tools/sign-file.ps1` + `tools/sign-win.js`。
- 顺序必须是 **先签主程序 → 再打安装包 → 最后签安装包**，因为 NSIS 把主程序压进安装包，
  事后签安装包不会让磁盘上的 exe 变成已签名。`npm run release` 已按这个顺序串好。
- 正式签名需要 OV/EV 代码签名证书，两种形态都支持（2023-06 起新证书私钥强制存硬件、不可导出，
  所以 pfx 越来越少）：
  - 硬件令牌：证书装在「当前用户 → 个人」，设 `CSC_THUMBPRINT=<40 位指纹>`；
  - 软件 pfx：`CSC_LINK=<pfx 路径>` + `CSC_KEY_PASSWORD=<密码>`。
  `--dev` 模式用自签证书，**只用于验证管线**：签名能写进去，但根不受信任，SmartScreen 照样拦。
- 新手上手、证书选购对比、申请材料与 20 条常见坑，见项目根目录 **`代码签名-新手实操指南.md`**。
- 版本号在 `package.json`，界面「关于」读的是 `app.getVersion()`，改完无需再改页面。

### 对外分发的包：未签名，以及用户该怎么核对

**本项目不购买代码签名证书**，Release 里的安装包是**未签名**的。原因见
`代码签名-新手实操指南.md` 〇·二：证书买的是"用户没法审计二进制、只能信 CA 的背书"，
而开源项目有更强的三条路径——源码可审计、可自行构建、构建来源可证明。

因此有两点必须让用户知道（GitHub Release 说明里也要写）：

1. **SmartScreen 会拦。** 首次运行 `ScreenQR-<版本>-x64.exe` 会出现
   "Windows 已保护你的电脑" → 点 **更多信息** → **仍要运行**。
   这不是中毒提示，是"这个程序没有数字签名"的通用提示；未签名的程序**每次**都会提示，
   没有"下载量够了就放行"这回事（SmartScreen 声誉是绑在证书上的）。
2. **杀软可能报毒。** 本程序会改系统代理、装本地根证书、模拟按键、枚举窗口、动态编译 C#，
   这套行为组合在启发式引擎里属高危。遇到拦截请加白名单，或直接用源码自行构建。

**用户怎么确认下载到的文件没被动过**（三种，任选）：

```bash
# ① 校验和：和 Release 页里 SHA256SUMS.txt 对一下
certutil -hashfile ScreenQR-0.4.0-x64.exe SHA256
# ② 来源证明：证明这个文件确实由本仓库该 commit 的 workflow 构建
gh attestation verify ScreenQR-0.4.0-x64.exe --repo <owner>/<repo>
# ③ 最彻底：自己构建
git clone <repo> && cd desktop && npm ci && npm run runtime && npm run dist
```

②③ 是签名证书的替代品：② 证明"来源与完整性"，③ 则连"里面到底有什么"都自己确认。

## 故障排查

| 现象 | 原因与处理 |
| --- | --- |
| `'负' 不是内部或外部命令` / `'udit' 不是...` / `'cho' 不是...` | `start.bat` 被存成了 **LF 换行 + UTF-8 中文**，cmd 按 GBK 解析导致行被截断。**现已修复**：bat 一律 CRLF 换行、纯 ASCII 内容。若日后用编辑器改过 bat，请注意保存为 CRLF，且不要在 bat 里写中文 |
| 双击后窗口一闪就没了 | 看 `%APPDATA%\ScreenQR\crash.log`（主进程未捕获异常会写在这里） |
| 依赖装不上 | 在 `desktop` 目录手动执行 `npm install --no-audit --no-fund`；Electron 下载慢可先 `set ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/` |
| 框选后扫不出 | 先确认二维码在框内且模块清晰（框要略大于码，留一点白边）；按 `空格` 切连续模式再试 |
| 捕获全黑 | 该内容受系统保护（UAC 弹窗、独占全屏、DRM），无法捕获，只能换手机扫 |
| 手机环境开了，但页面还是 PC 版 / 404 | 打开 `%APPDATA%\ScreenQR\proxy\manager.log` 看 `[scope]`：收窄模式下目标域应在列表里。若日志写"算不出目标域名"，多半是那条链接不是标准 http(s) 形态；若跳转域不在（站点用 JS 跳转而非 302），把设置「代理范围」临时切到**全部站点**再试，或 `curl "http://127.0.0.1:<管理口>/scope/add?host=那个域"`；能复现的话请提 issue，附 manager.log |
| 状态卡显示"只接管 0 个域名" | 2026-10-25 之前的构建有两个显示/传参缺陷（IPC 丢 `scopeUrl`、tick 事件缺范围字段）会导致这句文案恒为 0，且实际在跑全量。**更新到最新构建即可**；`manager.log` 的 `[scope]` 行显示"只接管 xxx"才是真收窄 |
| 全新 clone 后「手机环境依赖」显示缺 Python | `start.bat` 会自动补拉内置运行时（vendor\python 被 git 忽略，首次启动 fetch 一次）；手动补：`npm run runtime`。缺 node 时会提示改用系统 Python |

> 在 Git Bash 里手动跑时，注意本机环境可能设置了 `ELECTRON_RUN_AS_NODE=1`，那会让 Electron 退化成纯 Node 启动（无窗口、无输出）。用 `start.bat` 启动则已自动清空该变量。

>
> `--shot` 的目录必须用等号写：`--shot=ui-preview/app`。写成 `--shot ui-preview/app`

`--uitest` 的 `uitest.json` 里有三块诊断信息：

| 字段 | 用途 |
| --- | --- |
| `debug` | 取景框那一层 DOM 的即时状态（stat 胶囊 / 模式 / 错误条 / 画布尺寸） |
| `motion` | 隔 3 秒采样两次 `frameSeq` / `decodeCount`：连续模式必须增长，冻结模式必须不变 |
| `framePerf` | 连续抓 3 次屏的耗时，用来判断"画面不动"是抓屏慢还是循环没跑 |

`--sndtest` 的 `snd-test.json` 覆盖三段：

| 字段 | 用途 |
| --- | --- |
| `sniff` | 12 个样本各自归到 `ok` / `undecodable` / `no`（wav/mp3/flac/ogg/m4a/webm、wma/amr/ape/midi、误存网页、随机字节） |
| `decode` / `decodeBad` | 真解一段 0.6s WAV 成功；喂垃圾数据必须被拒 |
| `save` / `selectPreset` | 写盘后 `settings.json`、面板标签、选中态、重新导入行都跟着变；选完预设列表必须收起 |
| `noHScroll` / `pickbtnOneLine` | 400px 窄窗 + 浅色下不出现横向滚动、音色按钮不折行 |

同时产出三张截图：`10-提示音-展开音色` / `11-提示音-自定义` / `12-提示音-浅色窄窗`。测试结束会把 `settings.json` 原样写回并删掉测试音频。

`--wxtest` 对真实微信**只读**：只读进程树、只截一张图，结果写进 `wx-test/report.json`，同时留一张 `wx-test/live.png`。

| 字段 | 用途 |
| --- | --- |
| `shot` | 截屏是否成功、图像尺寸、`scales`（`!= [1]` 说明缩放没统一，定位必偏） |
| `hasMark` / `mark` | 是否已标定、标定的相对比例位置与时间 |
| `locate` | 定位结果：`how` 为 `patch`（图样命中）/ `ambiguous`（多处都像）/ `ratio-fallback`（退化成猜位置）/ `no-window`（没截到微信） |

## 本机实测记录（Windows，1536×864 DIP @1.25 缩放）

- 捕获分辨率 `1920×1080`，与 `1536×864 × 1.25` 完全一致 → DPI 换算正确
- 单帧解码 `33–41ms`（含裁剪 + 降采样）
- 单次抓屏 `1.3–2.0s`（`desktopCapturer.getSources`，与缩略图尺寸无关：320×180 也要 1.3s，
  说明开销全在每次重建 Windows Graphics Capture 会话，不在缩放）
- 已修复：无边框窗口被压到工作区高度（864→816）导致底部露边与比例错位
- 已修复：连续模式会把覆盖层自己拍进去 → `setContentProtection(true)` 自我排除
- 已修复：首帧要等 1~3 秒，期间整屏黑且没有任何提示 → 画「正在捕获屏幕…」并在胶囊上报状态
- 已修复：取帧失败会静默停在「等待画面」（`bootstrap` 的 await 没人 catch）→ 失败即提示并自动重试 4 次
- 已修复：设置里默认连续模式时只起了解码循环、没起换帧定时器 → 胶囊显示「连续」但画面是死的

## 已知限制

- 只覆盖鼠标所在的那一屏（多屏需先把鼠标移到目标屏再唤出）
- 连续模式实测约 `0.6–0.8 fps`：瓶颈是上面那条 1.3s/次的抓屏开销，不是解码。
  换帧间隔按实测耗时自适应（`lastCaptureMs + 200ms`，下限 600ms），不再固定 320ms 空转。
  要真正流畅得换成常驻桌面流（`getUserMedia` + `chromeMediaSource: "desktop"`），见文档 5.2
- 受保护内容（UAC 界面、独占全屏、部分 DRM）捕获为黑屏
- 仅 Windows 验证过，macOS 需补屏幕录制权限与公证
